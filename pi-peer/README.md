# pi-peer

同一个 `~/.pi/peers` 下的多个 pi 会话互通。典型场景：同一个项目目录开两个 pi（挂不同模型）临时互相问，或者跨项目找另一个目录里的会话通报进度。

零第三方依赖、无守护进程、无网络、不依赖 tmux —— 两个 pi 只要都加载了本扩展，就能互相发现并对话；不在同一目录的要写「项目标签/名字」。

## 安装

安装包含 pi-peer 与 pi-work-orders 的工具包：

```bash
pi install git:github.com/icylight/pi-team
```

只需 pi-peer 时，检出仓库后执行 `pi install /path/to/pi-team/pi-peer`。

重启 pi 或执行 `/reload` 生效。本地路径是原地加载，改完源码不用重装。

同一份扩展不要装两遍（比如全局一份、项目又一份）：工具名会撞，两份都不加载，报错形如 `Tool "peer_list" conflicts with ...`。

## 用法

```bash
# 终端 A：cd 到项目目录
pi

# 终端 B：同一个目录
pi --model deepseek/deepseek-flash

# 当前终端也可以直接新建一个会话（等同 pi 原生 /new，额外带上角色）：
/peer-new                    # 弹列表选角色，可选“自定义角色名…”
/peer-new --role dev         # 跳过选择，直接领 dev
```

然后：

```
/peers                 # 看同目录还有谁（/peers all 连其他项目一起列）
/peer-name reviewer     # 普通会话给自己起名
/peer-role              # 当前会话中途领角色：弹列表选（换卡、应用角色默认模型；选「－ 取消角色」摘掉）
/peer-send reviewer 帮我看看 src/a.ts 的并发处理
/peer-send ipd/owner 跨项目就用「项目标签/名字」
/peer-focus             # 进入专注模式：暂时不接别人的消息（见下）
```

角色会话按基础角色自动分配实例名：第一次是 `dev`，第二次是 `dev-2`，依次递增；所有实例都加载同一份 `.pi/characters/dev.md`。角色会话不能用 `/peer-name` 改名。

Agent 使用 `peer_list` / `peer_send` 通信。普通消息默认 `normal`：空闲时唤醒，忙时以 `followUp` 等当前轮结束。紧急消息显式指定 `priority: "urgent"`，或用 `/peer-send --urgent <目标> <正文>`，才以 `steer` 插入当前轮。返回明确区分写入收件箱和对方处理；普通发送到不支持新协议的旧版会话时拒绝并提示重载。

## 命令与工具

| 名称 | 说明 |
|---|---|
| `/peers [all]` | 列出同目录其他会话（名称、模型、id）；`all` 连其他项目一起列 |
| `/peer-config` | 看生效的项目配置从哪来：每个生效项带来源（配置 / 兜底 / 缺），以及写了但不由 pi-peer 读的键 |
| `/peer-role [角色|none]` | 查看或中途切换本会话角色：不带参弹列表选（当前角色带标记，含取消项）；换角色卡、认领实例名槽位、应用角色默认设置，并记入会话供重启恢复；`none` 取消角色，名字退回手动名或会话名 |
| `/peer-name <名字>` | 设置普通会话在 pi-peer 里的名字（持久化到 session） |
| `/peer-send <目标|项目/目标> <正文>` | 手动发消息；写「项目/名字」即跨项目 |
| `/peer-new [--role <角色>]` | 新建会话（同进程，等同原生 `/new`）；不给 `--role` 就弹列表选，可选自定义角色名。没有对应角色卡时照开，只退成普通会话，用 `/peer-name` 起名。角色与当前相同就保持当前模型与思考等级 |
| `/peer-reload` | 新建会话、继承当前名字、角色、模型与思考等级，不弹列表；上下文清空，身份不变 |
| `/peer-focus [on|off]` | 进入/退出专注模式：进入后对其他会话隐身（列表、寻址、派工都选不中），不接收消息；自己发出一条消息后自动退出，`off` 手动退出 |
| `PI_PEER_ROLE=<角色> pi` | 直接启动一个带角色的会话 |
| `peer_list` | 工具：列出同伴（含在线状态、心跳时间）；`scope="all"` 含其他项目 |
| `peer_send` | 工具：发消息；`priority` 为 `normal`（默认，不打断）或 `urgent`（显式打断）；`to` 支持 名称 / 项目/名称 / name#pid / id 前缀 / pid |
| `peer_assign_role` | 工具：给同项目其他空闲在线会话分配角色；调用者角色须配置 `canAssignRoles: true`，等待目标确认；不改目标的模型与思考强度 |
| `peer_new_session` | 工具：为同项目已有的其他在线空闲 agent 新建会话并写入任务；调用者须有 `canStartSessions: true`，等待新会话确认，不新增 agent 进程 |
| `peer_inbox` | 工具：查看收到的历史消息 |

目标名有歧义时不会瞎猜，会返回候选列表让你补全。

## 专注模式

`/peer-focus` 让当前会话对其他会话隐身：别人的 `peer_list` 与 `/peers` 里不出现它，按名字或角色寻址报「找不到」，派工与工单交接也投不进来（不报「离线」，以免被当成掉线重试）。已经写进收件箱的消息留在那里，退出后一次投完。自己发出一条消息（`peer_send` 或 `/peer-send`）即自动退出，也可以 `/peer-focus off`。

状态只在当前进程内：重启或 `/reload` 后恢复可见——静音忘了关比被打断更难发现。隐身期间也接不到角色分配与新会话派发，因为那些请求同样先要寻址到这个会话。

## 跨项目

同一个 `~/.pi/peers` 下每个项目一个桶，默认只看本项目。要跟其他项目的会话说话，写「项目标签/名字」：

```
peer_list(scope="all")                    # 列出其他项目的在线会话
peer_send(to="example-project/owner", …)   # 项目标签/名字
```

项目标签取项目的 `group.name`，没配就用目录名（走兜底时会在配置报告里标出来，见「配置来源」）。跨项目消息的落款会带上发送方前缀（形如 `.pi/dev`），对方抄回去就能回信 —— **接收方不需要升级**，跨项目只是写到了另一个目录，监听收件箱那一侧没变。

同桶投递不带前缀，本项目内发消息照旧。同名目标不唯一时报歧义并给候选，不会猜。

## 机制

```
~/.pi/peers/<目录名>-<路径哈希>/
  members/<sessionKey>.json        会话注册表（5s 心跳，30s 无心跳即判离线）
  pending/<sessionKey>/*.json      收件箱（未投递）
  delivered/<sessionKey>/*.json    已投递存档（保留最近 200 条）
  outbox/<sessionKey>/*.json       自己发出的消息（回复链追踪）
```

- **发现**：会话启动时注册自己并持续心跳；`pid` 存活 + `lastSeen` 新鲜才算在线，过期自动清理
- **投递**：原子写（临时文件 + rename），对方 `fs.watch` 自己的收件箱触发，2s 轮询兜底
- **不重复**：投递前先把消息 `rename` 到 `delivered/`，同一条消息只会被注入一次
- **唤醒**：来源名作为 `customType` 注入会话；普通消息 `followUp`，紧急消息 `steer`。耐久工单交接先校验当前阶段，只在空闲时注入，并按宿主当前分支 entry id 核对会话 JSONL 后确认。新空白会话的自定义消息可能只在内存，先发一次 followUp 唤醒，等首次用户消息使文件落盘后补确认；纯内存会话不确认耐久交接。唤醒、送达与业务认领分别处理；工单交接后的主动叫醒默认关（`wakeOnHandoff`）
- **分桶**：按工作目录分桶，默认只在本桶内发现与寻址；跨桶要显式写「项目标签/名字」，所以不会被无关项目的会话刷屏

## 配置

项目里不想让 pi-peer 生效时，在项目根放一份 `.pi/peer.json`：

```json
{ "enabled": false }
```

关掉的项目里本扩展不注册任何东西：没有 `peer_list` 等工具、没有 `/peers` 等命令、不写 `~/.pi/peers/`、不起心跳与收件箱监听。只读当前目录这一份配置，不向上递归查找 —— 同目录才算同一个桶，子目录起的会话本来就不互通。

文件不存在、或 `enabled` 缺失时按启用处理；JSON 解析失败、`enabled` 不是布尔值时也按启用处理，但会在交互会话里发一条警告。

**交接唤醒默认关**：收到工单交接只把正文落进会话（不自己开一轮），要项目里显式写 `{"wakeOnHandoff": true}` 才会额外注入一条「请处理刚收到的工单交接…」把目标叫醒。关着时交接靠目标下一次对话自己看到，空闲角色不会主动开工——这是为了不让每个新会话一开就被叫住。

| 配置 | 作用 |
|---|---|
| `<项目根>/.pi/peer.json` | 项目级开关，`{"enabled": false}` 关闭本项目 |
| `wakeOnHandoff`（同级） | 收到工单交接时是否主动叫醒，默认关 |
| `PI_PEER_OFF=1` | 进程级开关，关掉这个 pi 进程（不分目录） |
| `PI_PEER_ROOT` | 改共享目录根（默认 `~/.pi/peers`） |
| `PI_PEER_ROLE` | 启动时加载的基础角色名；角色卡默认取 `.pi/characters/<角色>.md` |

## 配置来源

配置文件里写了什么、哪些字段真的生效，不靠猜：`/peer-config` 把每个生效项连来源一起列。

```
项目配置：/path/to/example-project/.pi/peer.json（不存在（全部按兜底））
项目标签：example-project ｜ 兜底：group.name 没写，按目录名
可用角色：owner、qa ｜ 兜底：roles 没写，扫 .pi/characters/
角色卡（owner）：.pi/characters/owner.md ｜ 兜底：roles 里没声明 owner，按 .pi/characters/owner.md 命中
流程文档：.pi/flows/example-project.md ｜ 缺：flow 没写，按 group.name 找 .pi/flows/example-project.md，文件不在或为空
```

来源只有三种，所有项共用：**配置**（文件里显式写的）、**兜底**（没写，按规则算出来的）、**缺**（没写且兜底也没命中）。新增字段走同一个模型，报告与会话提示都不用改。

会话启动时会主动说三件事，其余时候安静：

- 配置文件本身有问题：JSON 解析不了、或字段写错（写错的字段不生效，一处一条）
- 除项目标签外，有东西按兜底生效了 —— 典型是同事 clone 下来只有 `.pi/characters/*.md`、没有配置文件；会话照样跑得起来，但得知道跑的是兜底
- 项目标签走兜底且配置文件存在（有人在配，那就是没配全）

项目标签单独的兜底不吭声：没配置文件、也没角色的项目本来不需要配，每次都为它弹一句是噪声。

`enabled: false` 的项目里扩展整个不注册，所以 `/peer-config` 也不存在 —— 那种项目要看配置只有直接读文件。

## 角色与流程配置

项目配置可以声明角色卡和 Markdown 流程；不配置角色时，`/peer-new --role dev` 默认读取 `.pi/characters/dev.md`。角色卡不存在时不挡新建：会话照开，只是没有卡，也就不是角色会话（不占实例名、不上报角色），用 `/peer-name` 自己起名即可。

让 agent 帮你改配置走 `peer-config-edit` skill：把意图定位到 `peer.json`、角色卡或流程文件，明确后直接写入。

`group.name` 同时也是跨项目寻址的项目标签（见「跨项目」）。

```json
{
  "enabled": true,
  "group": {
    "name": "example-project",
    "roles": {
      "owner": { "card": ".pi/characters/owner.md" },
      "dev": {
        "card": ".pi/characters/dev.md",
        "model": "feizhi/deepseek-flash",
        "thinkingLevel": "high"
      },
      "qa": { "card": ".pi/characters/qa.md" }
    },
    "flow": ".pi/flows/ipd.md"
  }
}
```

角色对象支持 `model`（完整 `provider/model-id`）与 `thinkingLevel`（`off`、`minimal`、`low`、`medium`、`high`、`xhigh`、`max`）。可只配其中一项；未配的保留会话设置。`group.roles` 的字段优先于顶层 `roles`，角色卡路径的字符串简写保持兼容。

默认设置在角色首次加载时应用并记录，`/peer-role` 中途领取也算一次；远程 `peer_assign_role` 不套用默认设置，只换角色卡与实例名。恢复或 `/reload` 不覆盖之后的手动选择。已有角色会话在升级后首次加载时也会初始化一次。模型切换失败时保留当前模型与思考强度并提示原因，下次加载重试；模型支持的思考等级由 pi 自动限制。角色卡不存在的普通会话不应用角色默认设置。`/peer-config` 展示配置值及来源，不代表恢复会话的当前选择；当前模型见 `/model`，当前思考强度见 `/thinking`。

新建会话的初始值由创建方定，写进新会话的条目在首次加载时应用；之后的手动选择同样不会被恢复覆盖。角色没变时（`/peer-reload`、`peer_new_session`）保持当前模型与思考等级；换角色时按新角色的配置，新角色没配的字段落回宿主默认。继承项缺的字段才读角色配置，所以远程新会话即使拿不到目标模型也不会退回无配置状态。

`flow` 只作为当前角色会话的 Markdown 参考注入，不自动修改工单或执行交接。角色的第一个实例名保留基础名，后续实例使用 `-2`、`-3`；会话退出后实例名可复用 —— `/peer-new` 会先结束当前会话再领号，所以同一会话反复换角色仍拿基础名，只有并行会话才会递增到 `dev-2`。

## 角色调度权限

在 `roles.<角色>` 或 `group.roles.<角色>` 配置 `"canAssignRoles": true`，该角色会话即可调用：

```text
peer_assign_role(to="dev-2", role="qa")
```

权限缺省关闭，只认布尔值；`group.roles` 逐字段优先，显式 `false` 可覆盖简写的 `true`。权限校验及 `/peer-config` 每次读取当前项目配置，撤销无需重载；角色卡路径、默认模型与思考强度仍按扩展加载时的配置执行。

目标须与调用者属于同一工作目录桶，在线且空闲，并已加载支持角色分配的扩展版本。发送端预检后，接收端再次根据本桶在线成员的当前角色校验权限、忙闲与目标原角色；正文消息不是授权。成功后换卡、认领实例名、保存角色，调用者收到目标确认才得到成功结果；目标的模型与思考强度不变，确认里的当前模型就是目标原本使用的模型。控制消息保留于收发记录，不唤醒模型。

目标忙碌、角色已变化或请求过期时拒绝，不排队等空闲后切换。确认超时或等待被取消时结果可能已生效，先用 `peer_list` 核实，再决定是否重试。旧版目标须先 `/reload`。

这项权限能把其他会话切成有调度权限的角色，属于委派能力；只授予负责调度的角色。它不新建进程、不清空已有上下文，也不提升文件或系统权限。收件箱与成员表由同一 OS 用户读写，不防御该用户直接伪造文件；安全边界是项目配置与扩展工具调用，不是 OS 进程隔离。

## 让已有 agent 新建会话

用户授权后，在调度角色的 `roles` 或 `group.roles` 对象中设置 `"canStartSessions": true`，即可调用：

```text
peer_new_session(to="dev-2", task="核实工单 T01 的当前状态，按任务范围继续实现并自测。")
```

该权限与 `canAssignRoles` 独立，缺省、覆盖及实时读取规则见「角色调度权限」。仅操作其他同项目、在线、明确空闲且支持本协议的现有 agent；不新增 agent 进程，也不切换调用者自己的会话。目标在收件、命令执行和切换前重新校验权限与忙闲，变忙或过期即拒绝，不排队重置。恢复或重载产生新的激活标识，旧请求即使遇到复用的会话 key 也不再执行。纯内存目标在操作前拒绝。

通过宿主公开 `newSession` 与新会话上下文处理生命周期，保留已有旧会话日志并记录父会话关系。保留目标基础角色；新会话继承目标当前模型与思考等级（继承项缺的字段才读角色配置），确认返回实际模型。任务通过初始化 API 写入真实的新会话文件，不把任务正文解释成宿主命令。成功须核对新 key、PID、当前分支任务及文件记录，不能只看请求发出或宿主 API 返回。

`task-persisted` 仅代表新会话及任务已确认保存，不代表任务执行完成或工单已认领。部分失败、取消等待或超时可能已经切换，先核实会话与收件记录，勿盲目再次新建。实例名以确认返回值为准；工单责任人需要变化时仍由调度者明确更新。权限及同 OS 用户信任边界沿用「角色调度权限」。现有会话须 `/reload` 加载新能力；之后修改权限无需重载。

## 已知边界

- 显式 urgent 消息会插进当前作业链；长命令运行时仍须等工具返回。普通消息不插队；独立普通消息的运行时 followUp 队列不承担工单耐久恢复承诺
- 没有防互刷的硬刹车：消息一到就起一轮，两个 agent 万一互相客套刷屏，只能人工中断或改 prompt 约束
- 目标离线时消息不发（`resolve` 回 `offline`）：写进一个没人取的 key 里，信会永远躺着，发件方却以为送达了。要等人回来就等，别改成写死信箱
- 专注模式（`/peer-focus`）下找不到目标与真离线在发送方看到的结果一样（都是解析不到），这是有意的：隐身的意义就是让别人选不中，而不是给一个还会被重试的强提示
- 同毫秒内跨进程的消息顺序不保证（进程内用序号保证）
- 单条普通消息正文上限按 `MAX_TEXT` 字符处理，超出截断；远程新会话的任务正文超出时拒绝，不截断后执行
- `ctx.newSession()` 一开始旧命令 ctx 就失效：setup 里要用的值必须在调用前取成局部变量，替换后的工作走 `withSession` 的 newCtx

## 代其他扩展投递

其他扩展（如 `pi-work-orders` 建单后叫人）走事件总线，不调 `peer_send` 工具：不占一次工具调用，也不触发权限询问。

| 频道 | 方向 | 载荷 |
|---|---|---|
| `peer:deliver` | 调用方 → peer | `{ id, targets: string[], text, requireIdle?, priority?, handoff?: { id, lease } }` |
| `peer:deliver:result` | peer → 调用方 | `{ id, ok, to?, detail }` |
| `peer:whoami` | 调用方 → peer | `{ id }` |
| `peer:whoami:result` | peer → 调用方 | `{ id, name }` |

`targets` 是有序候选，peer 投给第一个可投的；都不行就回 `ok: false`（失败也必回，否则调用方等超时）。调用方没有 peer 时应按「没叫到人」处理，不应当成业务失败。

`requireIdle: true` 时跳过忙碌候选；工单交接同时携带 `handoff`，目标须支持新协议。写入收件箱不等于注入：接收端通过 `work-orders:consume-handoff` 交当前项目台账校验，持久化后通过 `work-orders:handoff-injected` 确认。忙碌、离线、无消费端或租约失效时不注入，由台账耐久记录恢复；不从来信读取数据库路径。普通独立消息无需空闲预检，忙时交运行时 followUp 队列。

库层面的同一件事是 `PeerStore.deliverTo(target, { from, fromName, text }, { idleOnly })`——扫描器这类没有会话的调用方走它。

## 忙闲

成员带着 `busy` / `busySince`：`agent_start` 到 `agent_end` 之间算在忙，心跳会把它刷给其他会话。`peer_list` 显示成 `在线·空闲` / `在线·在忙`。

忙会按超时兜底（`BUSY_STALE_MS`，30 分钟）：`agent_end` 在中断路径上是否必发还没验证过，卡住的 busy 到点就作废，免得一次异常让某个会话永远收不到派工。
