# 工单台账

目的：**让「谁手上有什么、下一步找谁」有个跨会话的落点。** 聊天会滚、上下文会压缩，库不会。

判据：任取一条工单，扫一眼就能说出下一步找谁。细节在正文里，不在列表上。

## 什么时候用

- 多个会话协作同一件事（owner / dev / qa / ux 任意组合），状态需要跨会话、跨上下文压缩存活
- 派出去的活需要编号与归属，事后能查
- 需要回答「现在哪些能开工」「这条卡住会拖累谁」

单个会话自己干活不用它。

## 三个动作

| 动作 | 工具 |
| --- | --- |
| 建 | `orders_init` 建库（可同时写本轮需求）；`orders_create` 建单，正文写目标、交付物、边界、验收口径 |
| 改 | `orders_update` 改状态/下一步/终止依据，范围修订直接用 `body` 覆盖（正文只留当前有效口径）；`orders_dep` 加删依赖 |
| 查 | `orders_list`（默认未收口；`ready` 只看能开工的；`next` 只看等某人的；`state` 看某个状态；回看历史加 `history=true`）、`orders_show`、`orders_requirement` |

库默认在 `<项目>/.work-orders/`，随项目走、不进 git。

## 自动推进：不靠谁记得

台账自己会叫人，前两条不依赖 peer 在场：

1. **每轮对话开始**把「等你的 / 停滞的 / 可开工没人接的 / 等你拍板的」算成一段摘要写进系统提示（`.work-orders` 不存在或没有在等的人时不写）
2. **耐久交接**：写库后及会话存活期间自动扫描有效交接，忙碌、离线或重启时保留恢复记录；只向空闲目标注入普通通知，转派/取消使旧交接失效。用 `orders_notifications` 区分 waiting、sending、delivered、obsolete、failed 及原因。台账写入成功不等于消息已持久化，消息持久化不等于已认领；确认失败达到上限后先核实，不重复业务写入
3. **定时提醒跟着一个角色会话走**：配置里指定的角色（`followRole`，写在 pi-peer 的项目配置 `<项目>/.pi/peer.json` 的 `workOrders` 里，默认不开）自己每 15 分钟自查一次，有该提的单就注入一条汇总给自己；正在跑一轮时不插队。会话不在就没人在提——这是边界。提醒报三类读数：停滞（有人该动没动）、等依赖超阈值（`waitMinutes`，默认 120）、估算到 80% 与超 100%。后两类是为了不只在「落后」时才说话

等依赖的单仍出现在列表与摘要中，但不计停滞、不催接手；待认领与被打回的接手计时从进入当前状态、依赖真正解锁两者的较晚时刻开始。上游取消时显示「需人工裁定」，不当作前置完成；待复核和阻塞等需要人处理的状态保持催办。

改正文或删除已完成前置不会重置计时。时间依据见 `orders_show` 的状态与依赖动作记录，旧库缺事件时使用行时间回退。

## 七态

```
待认领 · 在做 · 待复核 · 被打回 · 阻塞 · 已收口 · 已取消
```

合法转换：

```
待认领 → 在做 | 已取消
在做   → 待复核 | 阻塞 | 已取消
阻塞   → 在做 | 已取消
待复核 → 已收口 | 被打回 | 已取消
被打回 → 在做 | 已取消
已收口 / 已取消 → 终态，不可退出
```

阻塞只从「在做」进、解除回「在做」，它是在做的暂停子态。终态不能再改回去，要重来就另开一条并注明取代关系。

## 下一步找谁：有序候选

`["dev", "qa"]` 读作「先找 dev，dev 不在 qa 接」。认领后收敛成接的那个人，因为「在做」只能有一个执行者。要重新分派就给新数组。

## 会被拦下来的事

这些不用记，越界时工具会拒绝并说明原因：

- 一个角色同时只能有一条「在做」——接第二条前先把手上那条阻塞或收口
- 结单必须带终止依据（证据指针：路径、命令、提交号都行）；取消必须给理由或被谁取代
- 依赖不能成环、不能指向自己
- 终态不可退出
- 状态转换不在表里
- 下一步找谁要写角色名，不写会话 key（`1423-311c` 这种重启即失效）；拿不准用 `/orders doctor` 查

并发改动带上手上的 `rev`，能拦住互相覆盖。

查不到东西时：空结果会附带一句「库里共多少条、该怎么查」，别把空回报当成「确实没有」。

## 与项目协作规则的分工

本 skill 只管**怎么操作这个库**。该不该派、如何跟进、交付是否通过，由使用方项目的角色分工与验收约定判断。

项目已有 `delegate-work`、`track-work`、`accept-work` 等管理类 skill 时可按职责使用；它们不随本包提供，也不是使用台账的前置依赖。

## 写单的要点

- 前置依赖写进 `dependsOn`（列表有专门的依赖列）；标题只说要做什么，不写「T×× 之后」「依赖 ××」。
- 正文写目标、交付物、边界、输入、验收与证据、回报。详细内容可用 `contents` 关联具名 md 入口，操作见 [README 的内容入口约定](../../README.md#内容入口一单多份-md)。验收口径在派工时写明。
- 范围改了用 `body` 覆盖，正文只保留当前有效口径。旧口径不靠正文留：`reason` 写清改了什么、为什么改，动作记录落库可查。靠 `appendBody` 一节节堆下去，读到第三版就没人知道哪句还算数。
- 有把握就给估算：`estimateActiveMin`（主动工时）、`estimateWallMin`（墙钟）、`estimateBasis`（依据与不确定的地方）。收口时回填 `actualActiveMin` / `actualWallMin` / `actualWaitMin` 与 `deliveryVariance`——偏差是算出来的，填的是原因。
- 前置还没收、但可以先做一部分的，写 `placeholderBasis` 说明按什么占位继续；不写就是必须等。
- 状态变更的 `reason` 必填，写的是**为什么**，不是「已更新」。

## 反模式

| 现象 | 实际是 |
| --- | --- |
| 群里说一句就当作已派工 | 库里没有，别人一停下来就丢了 |
| 表外的 md 再记一份状态 | 两处状态，迟早对不上 |
| 结单填「完成了」 | 终止依据要能被复核，不是自述 |
| 卡住了不改状态 | 后面的人看不出这条停了，以为在推进 |
