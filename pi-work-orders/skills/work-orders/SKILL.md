# 工单台账

目的：**让「谁手上有什么、下一步找谁」有个跨会话的落点。** 聊天会滚、上下文会压缩，库不会。

判据：任取一条工单，扫一眼就能说出下一步找谁。细节在正文里，不在列表上。

## 什么时候用

- 多个会话协作同一件事（owner / dev / qa / ux 任意组合），状态需要跨会话、跨上下文压缩存活
- 派出去的活需要编号与归属，事后能查
- 需要回答「现在哪些能开工」「这条卡住会拖累谁」

单个会话自己干活不用它。

## 怎么操作

| 动作 | 工具 |
| --- | --- |
| 建 | `orders_init` 建库（可同时写本轮需求）；`orders_create` 建单，正文写目标、交付物、边界、验收口径；`type` 可选，写类型给这条归个类 |
| 改 | `orders_update` 改状态/下一步/终止依据/类型，范围修订直接用 `body` 覆盖（正文只留当前有效口径）；口径定了 `contentLock=true` 锁住内容；`orders_dep` 加删依赖 |
| 评论 | `orders_comment` 留一段话：为什么这么判、看到什么、留给后面接手的人。不推状态、不涨 `rev`、不触发通知，写入后不改不删 |
| 查 | `orders_list`（默认未收口；`ready` 只看能开工的；`next` 只看等某人的；`state` 看某个状态；`type` 看某个类型；回看历史加 `history=true`）、`orders_show`、`orders_requirement` |

类型枚举默认 `需求单 · 实施单 · bug 单`，存在库的 `meta.types` 里：建库时用 `orders_init` 的 `types` 一次写定，之后改要直接写库。写枚举外的类型会被拒，不填就是未分类。

库默认在 `<项目>/.work-orders/`，随项目走、不进 git。

**版本号**：每写一次 `rev` 加一。列表、详情、每条动作都带它，动作记的是这次写完之后是第几版。跨会话说同一张单带上 rev（`T644 已取消（rev 6）`），对方一眼看出读的是不是同一版；`orders_update` 的 `expectedRevision` 用它拦并发。

库版本不匹配会自动逐版升级。**多会话共享同一个库时，最省事的是升级前约好窗口**：各会话换到新版后由一个打开库完成迁移。
被自动升级拖住过（还在跑旧代码的会话报「库版本比工具新」）时，临时设 `PI_WORK_ORDERS_NO_MIGRATE=1` 让它只报错不升级，
统一完再去掉 —— 它治的是已经发生的中断，不是预防。

## `/orders` 只有人能敲

工具列表里的 `orders_*` 你能调；`/orders` 开头的命令是给用户看的，agent 调不到。需要这些视图时说明让用户敲哪一个。

| 命令 | 看什么 |
| --- | --- |
| `/orders` | 未收口 |
| `/orders ready` | 依赖已解、能开工的 |
| `/orders stale` | 停滞超阈值的 |
| `/orders mine` | 等当前这个会话的 |
| `/orders all` | 含终态 |
| `/orders doctor` | 查会静默失效的写法：`nextActors` 写了会话 key、未收口却没写下一步、上游取消后依赖已失效 |
| `/orders web` | 浏览器跨项目看板，`web stop` 停 |

这几项工具侧不会主动标出来：`orders_list` 照常把会话 key 当名字显示，看不出它重启后就没人接得住。写完单用 `orders_list` 自检一遍，不确定再让用户跑一下 `doctor`。

## 自动推进：不靠谁记得

台账自己会叫人，但两处自动出声默认关，项目里显式配才开：

1. **每轮对话开始**把「等你的 / 停滞的 / 可开工没人接的 / 等你拍板的」算成一段摘要写进系统提示——要项目里写 `workOrders.digest: true`；不配就不注入（`.work-orders` 不存在或没在等的人时也不写）
2. **耐久交接**：写库后及会话存活期间自动扫描有效交接，忙碌、离线或重启时保留恢复记录；只向空闲目标注入普通通知，转派/取消使旧交接失效。用 `orders_notifications` 区分 waiting、sending、delivered、obsolete、failed 及原因。台账写入成功不等于消息已持久化，消息持久化不等于已认领；确认失败达到上限后先核实，不重复业务写入
3. **定时提醒跟着一个角色会话走**：配置里指定的角色（`followRole`，写在 pi-peer 的项目配置 `<项目>/.pi/peer.json` 的 `workOrders` 里，不配就不跑）自己每 15 分钟自查一次，有该提的单就注入一条汇总给自己；正在跑一轮时不插队。会话不在就没人在提——这是边界。提醒报三类读数：停滞（有人该动没动）、等依赖超阈值（`waitMinutes`，默认 120）、估算到 80% 与超 100%。后两类是为了不只在「落后」时才说话

等依赖的单仍出现在列表与摘要中，但不计停滞、不催接手；待认领与被打回的接手计时从进入当前状态、依赖真正解锁两者的较晚时刻开始。上游取消时显示「需人工裁定」，不当作前置完成；待复核和阻塞等需要人处理的状态保持催办。

改正文或删除已完成前置不会重置计时。时间依据见 `orders_show` 的状态与依赖动作记录，旧库缺事件时使用行时间回退。

## 状态

默认七态：待认领 · 在做 · 待复核 · 被打回 · 阻塞 · 已收口 · 已取消。

状态集由项目在库里声明（`meta.states`），数量和名字都可能与默认不同；每个状态带能力开关（`waiting`、`timing`、`singleOwner`、`execution`、`terminal`、`needsBasis`、`initial`），工具按开关工作。完整声明格式与默认集见 [README 的状态集](../../README.md#状态集)。

**状态之间不校验转换**：任何状态都能改到任何状态，跳级、回退、重开终态都只记事件。改错了用 `reason` 写清，事件里能查回来；是否该这么改由项目协作规则判断。

## 下一步找谁：有序候选

`["dev", "qa"]` 读作「先找 dev，dev 不在 qa 接」。推进到 `singleOwner` 状态后收敛成接的那个人，因为这类状态只许一个执行者。要重新分派就给新数组。

## 会被拦下来的事

这些不用记，越界时工具会拒绝并说明原因：

- 一个角色同时只能有一条在做——`singleOwner` 状态共享这条约束，接第二条前先把手上那条阻塞或收口
- 需要依据的状态没给依据：默认集里结单必须带终止依据（证据指针：路径、命令、提交号都行），取消必须给理由或被谁取代
- 依赖不能成环、不能指向自己
- 内容已锁定：改标题、正文、内容入口、类型会被拒，报出锁定人与时刻；先单独解锁（`contentLock=false`）再改，解锁与改内容不能同一次调用
- 类型不在配置的枚举里（不确定就用 `orders_list` 看已有单的分类，或问配置方）
- 下一步找谁要写角色名，不写会话 key（`1423-311c` 这种重启即失效）；拿不准用 `/orders doctor` 查

并发改动带上手上的 `rev`，能拦住互相覆盖。

查不到东西时：空结果会附带一句「库里共多少条、该怎么查」，别把空回报当成「确实没有」。

## 与项目协作规则的分工

本 skill 只管**怎么操作这个库**。该不该派、如何跟进、交付是否通过，由使用方项目的角色分工与验收约定判断。

项目已有 `delegate-work`、`track-work`、`accept-work` 等管理类 skill 时可按职责使用；它们不随本包提供，也不是使用台账的前置依赖。

## 写单的要点

- 前置依赖写进 `dependsOn`（列表有专门的依赖列）；标题只说要做什么，不写「T×× 之后」「依赖 ××」。
- 正文写目标、交付物、边界、输入、验收与证据、回报。详细内容可用 `contents` 关联具名 md 入口，操作见 [README 的内容入口约定](../../README.md#内容入口一单多份-md)。验收口径在派工时写明。
- 范围改了用 `body` 覆盖，正文只保留当前有效口径。旧口径不靠正文留：`reason` 写清改了什么、为什么改，动作记录落库可查。靠 `appendBody` 一节节堆下去，读到第三版就没人知道哪句还算数。
- 口径达成一致就 `contentLock=true` 冻住（可与定稿那次 `body` 同一次调用）。之后要改先解锁——`lock`/`unlock` 两条动作记录就是这条口径的历史。锁定只盖内容面，推进状态与回填工时照常，别拿它当收口。
- 有把握就给估算：`estimateActiveMin`（主动工时）、`estimateWallMin`（墙钟）、`estimateBasis`（依据与不确定的地方）。收口时回填 `actualActiveMin` / `actualWallMin` / `actualWaitMin` 与 `deliveryVariance`——偏差是算出来的，填的是原因。
- 前置还没收、但可以先做一部分的，写 `placeholderBasis` 说明按什么占位继续；不写就是必须等。
- 状态变更的 `reason` 必填，写的是**为什么**，不是「已更新」。

## 反模式

| 现象 | 实际是 |
| --- | --- |
| 群里说一句就当作已派工 | 库里没有，别人一停下来就丢了 |
| 表外的 md 再记一份状态 | 两处状态，迟早对不上 |
| 结单填「完成了」 | 终止依据要能被复核，不是自述 |
| 卡住了不改状态 | 后面的人看不出这条停了，以为在推进 |
