# pi-work-orders

本机 SQLite 工单台账，给同一台机器上多个 pi 会话（owner / dev / qa / ux）协作时当共享状态用。

**台账数据只在本机保存，不进 git。** 协作角色与推进规则不在这里，由项目的 skill 约定；这里只管状态、依赖和终止依据。

## 它解决什么

群聊（pi-tavern）和 peer 消息管沟通，管不了「现在什么状态」——消息是易失的、要翻的。这个库管状态：

- 谁手上有什么、下一步找谁（可以挂备选，首选不在时顺延）
- 谁等谁（依赖 DAG，能查可开工的和受影响的下游）
- 这条凭什么算结束（终止依据）

## 库

- 默认位置：`<项目>/.work-orders/work-orders.sqlite`（随项目走，记得 `.gitignore` 这一行）
- 可用环境变量 `PI_WORK_ORDERS_DB` 指到别处
- WAL 模式，多会话同写安全；schema 变更走 `PRAGMA user_version`

## 浏览器看板

在 pi 里敲 `/orders web`：起一个本地只读看板，浏览器随后打开；再敲一次只是重新打开页面。
层级是两层：总览页放跨项目「需关注」队列（等人动手、等待最久在前）与项目索引；
点进项目页看状态分列看板（待领/在做/待核/返工/暂停，空列不显示），收口与取消折叠在底部；
单条详情带正文、动作记录与内容入口的 md。

项目卡片同时显示依赖 ready、责任候选、匹配的角色实例、心跳/忙闲、关联在做工单及当前阶段的通知结果。基础角色可关联同角色实例，实例负载只按实例名关联；会话空闲不代表没有在做工单。缺失、过期或无法判断的状态明确显示，不推定为可接手。历史通知与当前阶段分开，不用旧的 delivered 冒充新交接已送达。

这些是页面读取时的只读观察，刷新后更新；不初始化通知库、不清理会话注册，不自动派工或认领。peer 根目录沿用 `PI_PEER_ROOT`，未设置时读取 `~/.pi/peers`。

```
/orders web         # 没有在跑的就起一个，随后打开浏览器
/orders web stop    # 停掉常驻的那个
```

- 服务是**独立进程**（默认端口 8787，`PI_WORK_ORDERS_WEB_PORT` 可改）：pi 会话开开关关它还在，多个会话共用同一个
- 只绑 `127.0.0.1`，库一律**只读**打开。schema 落后的库读不了，页面上会提示去那个项目里跑一次 `/orders` 升级
- 扫描根默认取当前目录与 `$CODE_ROOT`（缺省 `~/code`）下的一级子目录；端口已占且不是看板时，换 `--port`

看板是 Next.js（App Router + shadcn/ui）应用，源码在 `web/`。产物不入库，第一次要装依赖并构建：

```bash
cd pi-work-orders/web && npm install && npm run build
```

**之后不用手动重建**：`/orders web` 会比对 `.next/BUILD_ID` 与源码（含 `core/`）的修改时间，
产物旧了就先重建、再把已在跑的旧进程换掉，然后才起服务。

这条判据必要，是因为 `next start` 跑的是构建时生成的副本：改了 `core/*.ts` 不重建，
看板仍在用旧逻辑。典型症状是页面报「库版本比工具新」，看着像数据库坏了，实际只是产物旧了。

开发时用 `npm run dev`（不受这套判据约束）。`/orders web` 起的是构建产物（`next start -H 127.0.0.1`），构建目录缺失时它会提示先 build。

## 下一步找谁：有序候选

`nextActors` 是一个数组：**第一个是首选，后面是首选不在场时的备选**。

```
["dev", "qa"]     ← 先找 dev，dev 不在 qa 接
```

- 进「在做」时收敛成单人（`["接的人"]`）——执行者只能有一个，多条备选挂在做上会和「一人同时只能有一条在做」打架
- 列表输出会标出备选：`dev（备选 qa）`
- `orders_list` 的 `next` 过滤是**包含**匹配：备选也算命中。因为工具不知道谁在场，把备选也列出来，由 agent 自己判断要不要接
- 「谁在场」不归工具管（它不认在线状态），agent 需要时自己查 pi-peer

## 内容入口：一单多份 md

`contents` 保存工单的具名内容入口。名称表示这份 md 承担什么内容，不限制类别；工单仍是统一的责任、状态和验收单位，`body` 保留摘要与验收约定。详细内容在对应 md 维护，避免复制到正文。

建单时可传：

```json
{
  "title": "实现内容入口",
  "body": "目标、边界与验收条件",
  "nextActors": ["dev"],
  "contents": [
    { "name": "需求", "path": "docs/T01/需求.md" },
    { "name": "方案", "path": "docs/T01/方案.md" },
    { "name": "验证", "path": "docs/T01/验证.md" }
  ]
}
```

入口名称在同一工单内唯一，路径使用项目内相对 md 路径，允许文件尚未创建。工具只保存和展示入口，不读取、创建或改写文件；读取正文仍使用文件工具。关联不表示独占归属，不同工单可以使用同一路径。

`orders_update` 的 `contents` 替换完整列表：省略表示保留，`[]` 表示清空。更新前读取当前列表与 rev，将需要保留的入口一并传入，并用 `expectedRevision` 防止覆盖并发更新；变更理由按现有工单动作记录留痕。

## 七个状态

```
待认领 · 在做 · 待复核 · 被打回 · 阻塞 · 已收口 · 已取消
```

工具内部按「角色」工作（claimable / active / review / rework / paused / done / cancelled），状态名可以在库里换（`meta.states`），换名字不用改代码。

```
待认领 → 在做 | 已取消
在做   → 待复核 | 阻塞 | 已取消
阻塞   → 在做 | 已取消
待复核 → 已收口 | 被打回 | 已取消
被打回 → 在做 | 已取消
已收口 / 已取消 → 终态，不可退出
```

阻塞是「在做」的暂停子态，只从在做进、解除回在做。

## 工单类型

```
需求单 · 实施单 · bug 单
```

类型只做分类与筛选，不参与状态转换：不同类型不要求走不同状态机，同一个枚举对所有单都通用。

- 写入校验：`orders_create` / `orders_update` 写 `type` 时必须在枚举内，写错名字当场报错，不让它悄悄变成第 N 种分类
- 筛选：`orders_list` 的 `type` 只看某个类型；枚举外的名字同样报错，不静默返回空
- 不填 `type` 就是未分类，旧库升上来也是未分类

默认三种可在库里换（`meta.types`，字符串数组）：建库时用 `orders_init` 的 `types` 一次写定，之后改直接写库，跟 `meta.states` 同一套路。配成空数组表示这个项目不分类型，此时任何 `type` 都不合法。

## 强制规则

机制能拦的（约定管不住的那些）：

- **转换按角色校验**：不在表里的转换直接拒绝
- **一个角色同时只能有一条在做**：认领第二条会被拦，先阻塞或收口；「在做」的单只能挂一个执行者
- **认领自动取操作者**：`待认领 → 在做` 时 `nextActors` 直接变成 `[操作者]`，不用手传
- **结单必须有终止依据**（证据指针），取消必须给理由或取代它的单号
- **依赖环检测**：加边时查环，自环也拦
- **乐观锁**：改的时候带上手里的 rev，冲突会被拒绝
- **终态不可退出**：已收口/已取消不能重开，要改就另开一条
- **下一步找谁要写角色名**：会话 key（`1423-311c`、`项目名-1234`）在写入口就被拒——它重启即失效，落库后变成没人接得住的死链；用 `/orders doctor` 查历史遗留

## 自动推进

单子卡在「建了没人接」上，机制上要管住两件事：让它可见，让它叫得动人。

**一、每轮对话开始算一段摘要进系统提示**（`before_agent_start`）：等你的、停滞超阀值的、可开工没人接的。**默认关**，项目里写 `workOrders.digest: true` 才注入——新会话不背一份台账，要看得自己开或用 `/orders`。开了之后库没建、或没在等人的单时也不占上下文。

**二、耐久交接**：业务台账写入与通知分别呈现。每次写入后及会话存活期间每隔 5 秒扫描当前有效交接，将运行记录存到同项目 `.work-orders/notifications.sqlite`，不改原台账 schema。候选忙碌、离线或没有 peer 时保留 waiting 原因；会话恢复后重建与重试，不重新执行业务写入。任意加载台账的同项目会话均可接力，所有会话都退出时暂停，重启后恢复，不依赖 owner 人工重发。定时停滞提醒的 followRole 与这条恢复链路无关。

交接身份依据状态、责任人及交接/依赖事件，不使用普通行 revision。改正文不重发；转派、取消、认领或阶段取代使旧通知失效。派给本次交接操作者本人或人工执行者不通知；终态只使有效下游交接恢复。目标收到后再次校验当前业务与租约，只在空闲时同步写入会话；普通交接不 steer。按当前分支 entry id 在宿主当前会话 JSONL 中核对匹配记录后才记 delivered，不能把发送 API 返回或 `message_end` 当落盘证明。空白会话须先以 followUp 触发首次用户消息，再补持久化确认；确认等待有期限，后续由耐久租约恢复，未落盘不报送达。纯内存会话无法确认耐久交接。

用 `orders_notifications(id="T01")` 查询等待、传输、已持久化、失效或失败及原因。sending 只代表传输租约；delivered 不代表已认领或完成。离线/忙碌不会消耗实际注入重试次数。注入或确认失败的实际尝试有界，达到上限记 failed/结果未知，须人工核实；不承诺跨通知库与会话日志的 exactly-once。旧版目标不支持消费协议时明确等待升级，不降级成无校验文本。

**三、定时提醒跟着一个角色会话走**：配置里指定的角色（`followRole`）活着时，自己隔一会儿自查一次，有该提的单就把汇总注入成一条用户消息——等于它自己叫自己。会话不在就没人提，这是这个设计的边界。不配 `followRole` 就不跑，是默认行为。

提醒报四类读数，不只催「你落后了」：

| 理由 | 触发 |
|---|---|
| 停滞 | 该动的人名下的一条已经等了超过 `staleMinutes` |
| 等依赖超时 | 等依赖的时间超过 `waitMinutes`——谁都没错，但连续得太久要报 |
| 估算将到 | 已用时间到预估墙钟的 80%（`ESTIMATE_WARN_RATIO`） |
| 估算超期 | 已用超过预估墙钟 |

同一条单命中多条时只留最紧迫的一条；估算从 80% 走到 100% 算两条信息，不会被 `repeatMinutes` 压掉。提醒文案里写明这是报读数不是催进度，避免收到的人只顾解释进度。

配置就写在 pi-peer 的项目配置里，跟角色声明同一份。自动出声的两项（摘要、定时提醒）都默认关，配哪项就只响哪项：

```json
{
  "enabled": true,
  "workOrders": {
    "digest": true,
    "followRole": "owner",
    "intervalMinutes": 15,
    "staleMinutes": 30,
    "repeatMinutes": 60,
    "waitMinutes": 120
  }
}
```

- 路径 `<项目>/.pi/peer.json`；不写 `workOrders` 一段就静默，只落库不出声
- `digest` —— 每轮把台账摘要注入系统提示，默认 `false`
- `followRole` —— 定时提醒跟随的角色名，匹配角色实例名（`owner` 同时匹配 `owner-2`）；不写就不跑
- `intervalMinutes` 隔多久看一次（15）｜ `staleMinutes` 等超多久算停滞（30）｜ `repeatMinutes` 同一条单最短隔多久再提（60）｜ `waitMinutes` 等依赖超多久要报（120）
- 身份先问 pi-peer（`peer:whoami`），没装 peer 时退回会话名（`/peer-name`）
- 配置在会话启动时读一次；改了重开会话生效。配错了当场提示，不静默退回默认值
- 库是这个会话里才建的也认：建完下一轮就开始提

它只做一件事：把该提的单推到负责的那个角色眼前。不替它分派、不替它改状态。一条消息里每个角色最多列 5 条，其余折成一句。

等待分成「等处理」「等依赖」「上游已取消，需人工裁定」。这些是派生视图，不新增工单状态；列表与摘要保留依赖等待，但它不计入停滞或定时催办。待复核、阻塞等需要人处理的状态不会因未完成依赖被隐藏。

待认领与被打回的接手等待，从「进入当前状态」和「依赖真正解锁」的较晚时刻开始；多个前置取最后一个解锁点。删掉未完成前置也可解锁，删除已完成前置和改正文不会重置时钟。上游取消不解锁，下游等待人工裁定；其裁定计时从取消成为当前依赖问题时开始。

起点从现有状态与依赖事件推导，不写入新的历史事件。旧库缺事件时保守回退到行时间。

## 估算与实际

有把握就给估算，不强制——缺了只是没有进度提醒，不影响其它能力。

| 字段 | 含义 |
|---|---|
| `estimateActiveMin` | 预估主动工时（分钟）：真正在干的时间 |
| `estimateWallMin` | 预估墙钟（分钟）：到收尾的自然时间，含等待与中断 |
| `estimateBasis` | 评估依据与**不确定的地方** |
| `placeholderBasis` | 前置没收时按什么占位继续；不写就是必须等 |

收口时回填：`actualActiveMin`、`actualWallMin`、`actualWaitMin`、`deliveryVariance`。
**偏差是算出来的**（`deliveryDeviation`），人写的是原因；没估算就不算偏差，不编 0。

两个口径分开记的理由：墙钟减去主动工时就是被等待吃掉的部分。只记墙钟，事后分不清「做不完」和「等太久」；只记主动工时，看不出这条实际占用了多久。

进度从进入「在做」的时刻起算，只有「在做」与「阻塞」算进度——待认领还没开工、待复核已经在等人，把它们算成执行落后会催错人。

## 工具

| 工具 | 用途 |
|---|---|
| `orders_init` | 建库，同时写本轮需求（目标/边界/验收口径/基线）与可选配置：编号前缀 `idPrefix`、类型枚举 `types` |
| `orders_list` | 列单：默认未收口；`ready` 只看可开工的；`next` 只看等某人的；`state` 看某个状态（终态也算命中）；`type` 看某个类型；`history=true` 连终态一起列 |
| `orders_show` | 看一条的正文、内容入口、依赖、下游、估算与实际、终止依据、现场（依赖进展 / 上游产物 / 能否占位 / 要不要重读），以及最近几次动作（默认 5 条） |
| `orders_notifications` | 只读查询通知状态和原因，`id` 可限工单；返回最近更新的通知记录，不表示认领 |
| `orders_create` | 建单，可带 `dependsOn` 与 `type`（须在枚举内）；`nextActors` 传名字数组（首选在前）；可选估算 `estimateActiveMin` / `estimateWallMin` / `estimateBasis` 与占位许可 `placeholderBasis` |
| `orders_update` | 改状态或字段；`nextActors` 给多人就是重设备选，`type` 传空串清空分类。范围修订用 `body` 覆盖（正文只留当前有效口径，旧口径靠 `reason` 与动作记录留痕），`appendBody` 只用于补一小段。收口回填 `actualActiveMin` / `actualWallMin` / `actualWaitMin` / `deliveryVariance`。所有字段同一次事务，要么全成要么全不动；`body` 传空串表示这次不改正文 |
| `orders_dep` | 加/删依赖边 |
| `orders_requirement` | 看/改本轮需求，交付前对照 |

命令：`/orders [ready|stale|mine|all|doctor]`。`stale` 看停滞，`mine` 看等自己的，`doctor` 查会静默失效的写法。

空结果会附一句「库里共多少条、该怎么查」：不带 `history` 看终态曾经恒空，那种静默比报错更难自纠。

## actor 是谁

写操作的 actor 自动认：先问 pi-peer「我是谁」（有角色卡时就是 dev / qa / owner 这种角色实例名），其次 pi 的会话名，都没有就记「用户」。名字怎么约定归各个项目，这里不写死。

它服务两处：

- **认领**：`待认领 → 在做` 时自动成为这条的执行者（`nextActors = [actor]`），不用手传
- **标识**：这一笔改动是谁发起的

actor 不写「目录名-pid」：它重启即变，落进 `nextActors` 就是一条没人接得住的死链。身份问不到时宁可记「用户」——人坐在终端前，接得住。

## 库结构

`meta`（需求、状态集与类型枚举的覆盖、编号前缀）、`orders`、`deps`、`events`。

`events` 只追加：谁、何时、从什么状态到什么状态、为什么。它服务两件事：回答「这条挂了多久」（进当前状态的时刻），以及事后查谁改了。**`PI_WORK_ORDERS_NO_MIGRATE=1`：版本不匹配时只报错、不写库。这是应急手段，不是默认配置。**

自动升级是单会话场景的省事默认，共享库时会变成陷阱：谁先拿到新版代码打开库，升级就在那一刻发生，
其他还跑旧代码的会话立刻被锁在外面（报「库版本比工具新」）。出这种情况时临时设上这个变量，等所有
会话都换到新版，去掉变量、任一个会话打开库完成迁移，其余会话照常。

**不要长期全局设置**，两个原因：

- 全局设了，下次真要升级时没人能升（包括该发起升级的人）
- 部分会话设、部分不设，比都不设更糟：没设的照样自动升级，又变成「谁先打开谁说了算」

要长期避免这类意外，靠的是升级前约好窗口，不是靠这个开关。

schema 版本 5；旧库打开时逐版升级，v2 加 `events` 表，v3 给工单增加默认为空数组的 `contents` 列，v5 加工期列（估算、实际、偏差原因、占位许可），原有字段和事件不变；版本比工具新则拒绝打开。升级库之前，使用同一库的会话应先加载新版扩展，由一个会话先打开库完成升级，再让其他会话访问；旧版工具会拒绝打开升级后的库。

## 与 pi-peer 的接口

派工唤醒与身份识别走 pi-peer 的事件总线，四个频道（两边同时改）：

| 频道 | 方向 | 载荷 |
|---|---|---|
| `peer:deliver` | 台账 → peer | `{ id, targets: string[], text, requireIdle: true, priority: "normal", handoff: { id, lease } }` |
| `peer:deliver:result` | peer → 台账 | `{ id, ok, to?, detail }` |
| `peer:whoami` | 台账 → peer | `{ id }` |
| `peer:whoami:result` | peer → 台账 | `{ id, name }` |

peer 不在场或请求超时时，通知记录保留等待原因并恢复重试，业务写入成功不因此回滚。`peer:deliver:result.ok` 仅确认收件箱写入，不确认送达。接收端通过 `work-orders:consume-handoff` 请求当前项目台账同步校验和注入，通过 `work-orders:handoff-injected` 在消息持久化后确认。身份仍退回会话名或「用户」；摘要与定时提醒保持原有兜底。

## 未做

- 需求层只支持「一路一个」（库的元信息里一条）。要并行多个需求，得加需求表与 `req_id`。
- 状态转换表可被 `meta.transitions` 覆盖，但还没有命令或工具去改它，目前只能直接写库。
- 类型枚举同样只在建库时能一次写定（`orders_init` 的 `types`），改枚举得直接写库；类型不驱动状态机，也不能按类型做不同的必填校验。
- 定时提醒只在一个会话里响：那个角色的会话没开，就没人在提。
- 估算不拦：写 0 或负数会报错，但没写估算的单不会因为「没估」被拒；主动工时与墙钟的关系（墙钟应 ≥ 主动）也不校验——那是数据质量，不是硬规则。
- 偏差只做减法，不判断好坏，也不跨单汇总（没有「哪类活总是估不准」的统计）。
