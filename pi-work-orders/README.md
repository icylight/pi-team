# pi-work-orders

本机 SQLite 工单台账，给同一台机器上多个 pi 会话（owner / dev / qa / ux）协作时当共享状态用。

**台账数据只在本机保存，不进 git。** 协作角色与推进规则不在这里，由项目的 skill 约定；这里只管状态、依赖和终止依据。

## 它解决什么

群聊（pi-tavern）和 peer 消息管沟通，管不了「现在什么状态」——消息是易失的、要翻的。这个库管状态：

- 谁手上有什么、下一步找谁（可以挂备选，首选不在时顺延）
- 谁等谁（依赖 DAG，能查可开工的和受影响的下游）
- 这条凭什么算结束（终止依据）

## 库

- 默认位置：`<项目>/.work-orders/work-orders.sqlite`（随项目走，记得 `.gitignore` 这一行）
- 可用环境变量 `PI_WORK_ORDERS_DB` 指到别处
- WAL 模式，多会话同写安全；schema 变更走 `PRAGMA user_version`

## 浏览器看板

在 pi 里敲 `/orders web`：起一个本地只读看板（跨项目总览、单条详情的正文与动作记录、内容入口的 md），
浏览器随后打开；再敲一次只是重新打开页面。

```
/orders web         # 没有在跑的就起一个，随后打开浏览器
/orders web stop    # 停掉常驻的那个
```

- 服务是**独立进程**（默认端口 8787，`PI_WORK_ORDERS_WEB_PORT` 可改）：pi 会话开开关关它还在，多个会话共用同一个
- 只绑 `127.0.0.1`，库一律**只读**打开。schema 落后的库读不了，页面上会提示去那个项目里跑一次 `/orders` 升级
- 扫描根默认取当前目录与 `$CODE_ROOT`（缺省 `~/code`）下的一级子目录；端口已占且不是看板时，换 `--port`

看板是 Next.js（App Router + shadcn/ui）应用，源码在 `web/`。产物不入库，**先构建再起**：

```bash
cd pi-work-orders/web && npm install && npm run build   # 一次即可，改了 UI 再 build
```

开发时用 `npm run dev`。`/orders web` 起的是构建产物（`next start -H 127.0.0.1`），构建目录缺失时它会提示先 build。

## 下一步找谁：有序候选

`nextActors` 是一个数组：**第一个是首选，后面是首选不在场时的备选**。

```
["dev", "qa"]     ← 先找 dev，dev 不在 qa 接
```

- 进「在做」时收敛成单人（`["接的人"]`）——执行者只能有一个，多条备选挂在做上会和「一人同时只能有一条在做」打架
- 列表输出会标出备选：`dev（备选 qa）`
- `orders_list` 的 `next` 过滤是**包含**匹配：备选也算命中。因为工具不知道谁在场，把备选也列出来，由 agent 自己判断要不要接
- 「谁在场」不归工具管（它不认在线状态），agent 需要时自己查 pi-peer

## 内容入口：一单多份 md

`contents` 保存工单的具名内容入口。名称表示这份 md 承担什么内容，不限制类别；工单仍是统一的责任、状态和验收单位，`body` 保留摘要与验收约定。详细内容在对应 md 维护，避免复制到正文。

建单时可传：

```json
{
  "title": "实现内容入口",
  "body": "目标、边界与验收条件",
  "nextActors": ["dev"],
  "contents": [
    { "name": "需求", "path": "docs/T01/需求.md" },
    { "name": "方案", "path": "docs/T01/方案.md" },
    { "name": "验证", "path": "docs/T01/验证.md" }
  ]
}
```

入口名称在同一工单内唯一，路径使用项目内相对 md 路径，允许文件尚未创建。工具只保存和展示入口，不读取、创建或改写文件；读取正文仍使用文件工具。关联不表示独占归属，不同工单可以使用同一路径。

`orders_update` 的 `contents` 替换完整列表：省略表示保留，`[]` 表示清空。更新前读取当前列表与 rev，将需要保留的入口一并传入，并用 `expectedRevision` 防止覆盖并发更新；变更理由按现有工单动作记录留痕。

## 七个状态

```
待认领 · 在做 · 待复核 · 被打回 · 阻塞 · 已收口 · 已取消
```

工具内部按「角色」工作（claimable / active / review / rework / paused / done / cancelled），状态名可以在库里换（`meta.states`），换名字不用改代码。

```
待认领 → 在做 | 已取消
在做   → 待复核 | 阻塞 | 已取消
阻塞   → 在做 | 已取消
待复核 → 已收口 | 被打回 | 已取消
被打回 → 在做 | 已取消
已收口 / 已取消 → 终态，不可退出
```

阻塞是「在做」的暂停子态，只从在做进、解除回在做。

## 强制规则

机制能拦的（约定管不住的那些）：

- **转换按角色校验**：不在表里的转换直接拒绝
- **一个角色同时只能有一条在做**：认领第二条会被拦，先阻塞或收口；「在做」的单只能挂一个执行者
- **认领自动取操作者**：`待认领 → 在做` 时 `nextActors` 直接变成 `[操作者]`，不用手传
- **结单必须有终止依据**（证据指针），取消必须给理由或取代它的单号
- **依赖环检测**：加边时查环，自环也拦
- **乐观锁**：改的时候带上手里的 rev，冲突会被拒绝
- **终态不可退出**：已收口/已取消不能重开，要改就另开一条
- **下一步找谁要写角色名**：会话 key（`1423-311c`、`项目名-1234`）在写入口就被拒——它重启即失效，落库后变成没人接得住的死链；用 `/orders doctor` 查历史遗留

## 自动推进

单子卡在「建了没人接」上，机制上要管住两件事：让它可见，让它叫得动人。

**一、每轮对话开始算一段摘要进系统提示**（`before_agent_start`）：等你的、停滞超阀值的、可开工没人接的。只用台账、不用 peer 也看得到——打开项目就知道有东西在等，自己就是执行者。库没建、或没在等人的单时不占上下文。

**二、写库即派工**：建单、交付给复核人、收口解锁下游时，把「该你了」投给下一步的名字。通道是 peer 的事件总线（`peer:deliver`），**只投给空闲的会话**：对方在跑一轮时不打扰，库已经落了、不是失败，下一轮开始时启动摘要里就有它。派给自己（认领、自派）不发，等人工（`用户`）的单也不发——没有叫这个名的会话。终态不叫当事人，只叫刚解锁的下游。

**三、定时提醒跟着一个角色会话走**：配置里指定的角色（`followRole`）活着时，自己隔一会儿自查一次，有停滞的单就把汇总注入成一条用户消息——等于它自己叫自己。会话不在就没人提，这是这个设计的边界。

配置就写在 pi-peer 的项目配置里，跟角色声明同一份（默认不开）：

```json
{
  "enabled": true,
  "workOrders": { "followRole": "owner", "intervalMinutes": 15, "staleMinutes": 30, "repeatMinutes": 60 }
}
```

- 路径 `<项目>/.pi/peer.json`；不写 `workOrders` 一段就不跑
- `followRole` —— 角色名，匹配角色实例名（`owner` 同时匹配 `owner-2`）
- `intervalMinutes` 隔多久看一次（15）｜ `staleMinutes` 等超多久算停滞（30）｜ `repeatMinutes` 同一条单最短隔多久再提（60）
- 身份先问 pi-peer（`peer:whoami`），没装 peer 时退回会话名（`/peer-name`）
- 配置在会话启动时读一次；改了重开会话生效。配错了当场提示，不静默退回默认值
- 库是这个会话里才建的也认：建完下一轮就开始提

它只做一件事：把停滞的单推到负责的那个角色眼前。不替它分派、不替它改状态。一条消息里每个角色最多列 5 条，其余折成一句。

等待分成「等处理」「等依赖」「上游已取消，需人工裁定」。这些是派生视图，不新增工单状态；列表与摘要保留依赖等待，但它不计入停滞或定时催办。待复核、阻塞等需要人处理的状态不会因未完成依赖被隐藏。

待认领与被打回的接手等待，从「进入当前状态」和「依赖真正解锁」的较晚时刻开始；多个前置取最后一个解锁点。删掉未完成前置也可解锁，删除已完成前置和改正文不会重置时钟。上游取消不解锁，下游等待人工裁定；其裁定计时从取消成为当前依赖问题时开始。

起点从现有状态与依赖事件推导，不写入新的历史事件。旧库缺事件时保守回退到行时间。

## 工具

| 工具 | 用途 |
|---|---|
| `orders_init` | 建库，同时写本轮需求（目标/边界/验收口径/基线） |
| `orders_list` | 列单：默认未收口；`ready` 只看可开工的；`next` 只看等某人的；`state` 看某个状态（终态也算命中）；`history=true` 连终态一起列 |
| `orders_show` | 看一条的正文、内容入口、依赖、下游、终止依据，以及最近几次动作（默认 5 条） |
| `orders_create` | 建单，可带 `dependsOn`；`nextActors` 传名字数组（首选在前） |
| `orders_update` | 改状态或字段；`appendBody` 用于范围修订（追加，不覆盖旧句）；`nextActors` 给多人就是重设备选。字段与追加同一次事务，要么全成要么全不动；`body` 传空串表示这次不改正文 |
| `orders_dep` | 加/删依赖边 |
| `orders_requirement` | 看/改本轮需求，交付前对照 |

命令：`/orders [ready|stale|mine|all|doctor]`。`stale` 看停滞，`mine` 看等自己的，`doctor` 查会静默失效的写法。

空结果会附一句「库里共多少条、该怎么查」：不带 `history` 看终态曾经恒空，那种静默比报错更难自纠。

## actor 是谁

写操作的 actor 自动认：先问 pi-peer「我是谁」（有角色卡时就是 dev / qa / owner 这种角色实例名），其次 pi 的会话名，都没有就记「用户」。名字怎么约定归各个项目，这里不写死。

它服务两处：

- **认领**：`待认领 → 在做` 时自动成为这条的执行者（`nextActors = [actor]`），不用手传
- **标识**：这一笔改动是谁发起的

actor 不写「目录名-pid」：它重启即变，落进 `nextActors` 就是一条没人接得住的死链。身份问不到时宁可记「用户」——人坐在终端前，接得住。

## 库结构

`meta`（需求、状态集覆盖、编号前缀）、`orders`、`deps`、`events`。

`events` 只追加：谁、何时、从什么状态到什么状态、为什么。它服务两件事：回答「这条挂了多久」（进当前状态的时刻），以及事后查谁改了。schema 版本 4；旧库打开时逐版升级，v2 加 `events` 表，v3 给工单增加默认为空数组的 `contents` 列，原有字段和事件不变；版本比工具新则拒绝打开。升级库之前，使用同一库的会话应先加载新版扩展，由一个会话先打开库完成升级，再让其他会话访问；旧版工具会拒绝打开升级后的库。

## 与 pi-peer 的接口

派工唤醒与身份识别走 pi-peer 的事件总线，四个频道（两边同时改）：

| 频道 | 方向 | 载荷 |
|---|---|---|
| `peer:deliver` | 台账 → peer | `{ id, targets: string[], text }` |
| `peer:deliver:result` | peer → 台账 | `{ id, ok, to?, detail }` |
| `peer:whoami` | 台账 → peer | `{ id }` |
| `peer:whoami:result` | peer → 台账 | `{ id, name }` |

peer 不在场时：投递等 400ms 超时按「没叫到人」处理，身份退回会话名或「用户」。定时提醒的 `followRole` 也跟着退回会话名。库照常写，摘要照常注入。
